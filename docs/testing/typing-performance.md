# 長文入力の性能改善と数字・波ダッシュ

実施日：2026-10-26。対象は本番IMEなしの日本語長文入力。開発サーバーで漢字文への反映が重いという報告に対し、同じ課題・入力位置・設定で変更前後を計測した。

## 計測条件

- 正しさの条件：入力の受理・拒否、削除・修正、候補設定、採点、漢字／ルビ／読みの進捗を維持する。
- 探索は、入力候補・進捗結果の再利用（A）と、静的な読み情報の再利用（B）の2段階で実施した。増分解析への書き換えは行っていない。
- 処理時間：固定した353文字・835キーの長文について、入力済み表示の計算と漢字・ルビの描画を各位置で30回計測。冒頭5回はウォームアップ。`scripts/fixtures/typing-long-benchmark.json` に入力を保存した。
- ブラウザー：ユーザーの `http://localhost:3000/production/ime-off` を隔離したヘッドレスChromeで実行。通勤電車の先頭長文371文字、課題ハッシュ `88eeec44b143`、ヘボン入力、漢字・ルビ・入力済み表示を有効化し、音声を無効化した。
- 各キーの処理後に次のフレームとタスクを待つ。100・400・650打鍵付近で12回ずつ計測し、662打鍵すべてが誤入力0件であることを確認した。計測値にはフレーム待ちを含む。

## 変更

- `useTypingSession` で、現在・最短・次課題のローマ字入力ターゲットをメモ化した。課題・言語・モード・テーマ・入力設定が変われば再作成する。
- `getRomajiInputProgress` はターゲット単位の弱参照キャッシュで直近4入力を再利用する。旧入力・新入力を交互に採点するため、1入力だけのキャッシュにはしない。誤入力も扱い、戻り値と入力候補の配列はコピーして返す。
- 解析状態が0件または1件なら、状態重複の検査用に長い入力履歴を文字列化する処理を省いた。
- 読みの前処理と読み単位のトークン数に、それぞれ上限256件のLRUキャッシュを設けた。キーは元の文字列そのもので、片仮名の表示を維持する。内部の読み情報は外へ公開せず、公開する読みガイドは従来どおり新しいオブジェクトを返す。

## 数字と「～」

- 作成規則に、漢数字に限定せず半角のアラビア数字0～9を使うこと、表示の数字を読み仮名で代替しないこと、波ダッシュを自然に使えることを追加した。
- 全9テーマの各1～2本、計10本に小さな修正を行い、`1～2行`、`15～20分`、`1958年8月25日` などを入れた。文体、会話、既存の豆知識を維持した。
- 全テーマで10長文・300～600文字を維持し、短文ファイルのSHA-256は変更前と一致。表示・読み・ローマ字入力の数字列が一致し、数字0～9がすべて本文に含まれることを確認した。
- `1～3分` の数字は `1~3pun` として入力でき、`1` を `ichi`、`3` を `san` に置き換える入力を拒否する回帰テストを追加した。

- `bun run typecheck`：exit 0。
- 変更したTS／TSXファイル8件のESLint：最初に検出した依存配列の書式を修正後、すべてexit 0。
- 独立レビューで、キャッシュの上限、返却値のコピー、文字種、設定変更時の再作成、既存呼び出し元にターゲットを変更する処理がないことを確認した。
